# SOP-002: Suspicious Web Request Triage

**Project:** Wazuh Mini-SOC  
**SOP ID:** SOP-002  
**Role:** L1 SOC Analyst  
**Status:** Basic web-log collection, alert generation, and dashboard visibility validated; suspicious-request/exploit detection not independently validated  
**Scope:** Authorized lab and monitored web servers

## 1. Purpose

Provide a repeatable workflow for reviewing potentially suspicious HTTP requests, validating web-log collection, investigating related Wazuh alerts, and documenting findings.

## 2. Detection and log sources

**Test environment:** Kali Linux VM with Wazuh agent `kali-vm` (agent ID `001`).

**Web server:** Nginx.

**Configured log sources:**
- `/var/log/nginx/access.log`
- `/var/log/nginx/error.log`
- `/var/log/apache2/access.log`
- `/var/log/apache2/error.log`

**Relevant observed detection:**
- Rule ID: `31101`
- Rule level: `5`
- Rule description: `Web server 400 error code.`
- Decoder: `web-accesslog`
- Observed HTTP status: `404`

The observed rule description does not precisely match the HTTP status in the test event. This is a rule-tuning observation, not proof of a defective rule.

## 3. Initial alert review

For each web-related alert, record:

- Alert timestamp and timezone
- Incident ID
- Affected agent and agent ID
- Rule ID, description, and severity
- Source IP address
- HTTP method and requested URL/path
- HTTP response status code
- Relevant raw log message
- Related events in the same time window

Do not assume that a failed request, unusual URL, or HTTP 4xx response proves malicious activity.

## 4. Validate log collection

1. Identify the web server and the log file receiving the request.
2. Verify the expected log file exists and is being updated.
3. Confirm the Wazuh agent configuration includes the relevant log path.
4. Review the agent log for collection errors or file-access problems.
5. Verify the raw request appears in the web-server log.
6. Check whether Wazuh generated a matching alert.
7. If the alert is present in the manager's `alerts.json` but not in the dashboard, investigate indexing, dashboard time range, and search filters separately.

A log appearing on the host establishes log generation. A corresponding manager alert establishes alert generation. Dashboard visibility requires a separate check.

## 5. Investigate suspicious requests

Review the request in context. Potential investigation leads include:

- Repeated requests to nonexistent or sensitive paths
- Unexpected requests for administrative interfaces
- Repeated HTTP 401, 403, or 404 responses
- Unusual HTTP methods or malformed request patterns
- Requests associated with repeated server errors
- Requests followed by suspicious application behavior or other alerts

These are leads, not proof of an attack. Consider the application, expected traffic, approved testing, source reputation where available, and related activity before classifying the event.

## 6. Correlate and assess severity

1. Group events by source, target host, and time window.
2. Compare request paths, methods, status codes, and frequency.
3. Determine whether the activity was generated by an authorized test, expected application behavior, a scanner, or an unknown source.
4. Look for evidence of successful access, unexpected changes, or related alerts.
5. Escalate repeated or credible exploitation indicators according to the organization's incident-response policy.

Do not infer compromise solely from an HTTP 404 response or one alert.

## 7. Response and escalation

**Expected or authorized activity**
- Document the test or known business reason.
- Preserve relevant evidence.
- Close according to the lab or organizational workflow.

**Suspicious but unconfirmed activity**
- Record relevant events and context.
- Collect supporting logs and related alert details.
- Escalate to the designated analyst if required.

**Credible evidence of exploitation or compromise**
- Follow the approved incident-response procedure.
- Preserve evidence and document the timeline.
- Obtain authorization before blocking addresses, isolating hosts, or changing production systems.

Do not automatically block an IP based solely on an HTTP 4xx response.

## 8. Evidence and ticket requirements

Record:

- Incident ID and analyst
- Detection timestamp and time range
- Affected host and Wazuh agent
- Rule ID, severity, and description
- Relevant source IP, request path, method, and status code
- Sanitized raw log entries or screenshots
- Investigation steps and findings
- Classification, escalation decision, and closure rationale
- Any rule-tuning observations

Remove passwords, cookies, authorization headers, tokens, private keys, and unrelated personal data from evidence before sharing it.

## 9. Closure criteria

Close the investigation only after:

- The relevant activity has been classified
- Supporting evidence has been preserved
- Required escalation or response actions have been completed
- Dashboard visibility issues, if relevant, have been recorded
- The incident disposition and limitations have been documented

## 10. Lab validation record

**Test date:** 25 October 2026

**Environment:** Kali VM, local Nginx, Wazuh agent `kali-vm`.

Two local HTTP requests were generated:

| Request | Observed status |
|---|---:|
| `GET /` | 200 |
| `GET /does-not-exist-for-wazuh-lab` | 404 |

Both requests appeared in `/var/log/nginx/access.log`.

The Wazuh manager's `/var/ossec/logs/alerts/alerts.json` contained an event for the nonexistent-path request with:

- Rule ID `31101`
- Rule level `5`
- Description `Web server 400 error code.`
- Decoder `web-accesslog`
- Source IP `127.0.0.1`
- Location `/var/log/nginx/access.log`
- HTTP status `404` in the parsed event

**Confirmed:** Local web-request generation, access-log writing, and manager alert generation.

**Confirmed:** The matching rule 31101 event was visible in Threat Hunting after searching for rule.id 31101 and selecting the correct time range.

**Limitations:** This test does not validate SQL injection detection, path traversal detection, exploit detection, remote attack detection, automated blocking, or successful compromise prevention. The tested request was benign and generated by the analyst.
